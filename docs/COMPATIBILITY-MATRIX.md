# DOM Compatibility Matrix

This matrix records detector, ownership, identity, media, and authoritative fill behavior covered by the offline compatibility corpus. Fixtures use neutral text, synthetic identifiers, fixed viewport geometry, and no authentication state. External-looking media URLs use the reserved `example.test` host and are inspected as URL metadata only.

`generic-path` means the fixture exercises the shared DOM model. `site-specialized-path` names the currently exercised site branch. These labels describe the corpus; they do not claim support for every page on a platform.

The categories distinguish shared support, safe product limitations, current architecture limits, and behavior hidden by browser security. `Fill Support` values below are checked against each fixture's machine-readable fill contract; supported values run `fillParsedAnswerInPage` and authoritative readback where applicable.

The first two Pintia fixtures are sanitized from the repository's existing Pintia-style regression structures. Their original task text, long numeric IDs, and page-specific data have been replaced. The extension's current Pintia branch requires a numeric question-list ID, so the list fixture uses synthetic eight-digit identifiers solely to exercise that selector.

Closed shadow root: Page-owned closed roots are not exposed to extension DOM traversal. Cross-origin iframe DOM: The current content runtime injects into the top frame only; host permissions do not add per-frame runtime injection or coordination.

The manifest grants `http://*/*` and `https://*/*` host permissions. The bootstrap in `src/shared/utils/messaging.ts` calls `chrome.scripting.executeScript` with `{ target: { tabId } }`, so the current path targets the top frame and does not coordinate an independent runtime in each cross-origin frame. This is an architecture limit, not an absolute browser prohibition: with matching host permissions an extension can execute in a matching frame. A future design would use a per-frame content runtime, explicit frame identity, and message authority. A parent content script must not directly read or infer a cross-origin child document.

The corpus is executed by `src/content/detector/compatibilityCorpus.test.ts`. Contract and fixture data live in `src/content/detector/testFixtures/compatibilityFixtures.ts`. Known limitations are recorded as expected outcomes; they are tested behavior, not detector test failures. A future compatibility fix must add or update a deterministic fixture before changing the production detector.

## Phase 9B compatibility finding (addressed on branch; Issue #13 remains OPEN)

### COMPAT-08 — Pintia question-list single-choice fill (P2, addressed)

- **Fixture:** `COMPAT-08` (`real-platform-derived`, Pintia question list).
- **Before repair:** The detected/runtime identity owner was the outer `DIV#10000002`, with stable ID `q_v1_71543e92` and content fingerprint `cf_v1_ceff99b1`. Control mapping correctly found A/B/C/D under its contained `.question-item` with confidence 1.0 and the same question ID.
- **Exact rejection:** `src/content/answerFiller.ts`, `fillVerifiedAnswerIntoScope()` → `resolveAuthority()`, at the live identity comparison. It compared the block identity to `observeLiveQuestion(block, mapping.owner)`. Both outer-card and inner-wrapper structured observations omitted the unmarked stem and produced `q_v1_79466b46` / `cf_v1_94e440d9`, so the stable ID and fingerprint comparisons rejected before answer-plan construction or mutation.
- **Repair:** The sealed runtime owner remains the identity authority, while the control mapper may use its proven semantic descendant. Live observation keeps the detector's structured projection when it matches `identitySourceText`; otherwise it reads current rendered owner text. It never reuses the stored text as live identity content. Solve-start snapshots use the same identity owner.
- **After repair:** The single-choice card fills B once, authoritative readback passes, and no wrong option, submit, or advance occurs. `P9B-OWNER-01` proves the same outer-owner/inner-control model on a generic fixture; `P9B-NESTED-NEG-01` rejects an independent nested question's controls; `P9B-FINGERPRINT-NEG-01` still rejects changed live outer content.
- **Disposition:** The P2 compatibility defect is addressed on the Phase 9B branch. Issue #13 remains OPEN until independent review, merge, and post-merge CI succeed.
